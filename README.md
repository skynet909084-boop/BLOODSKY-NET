## Distributed Probes 2.3 · 0.30.0-dev

- **Наблюдения по ID отправителя:** показываются время последнего принятого TLS-пакета (UTC), свежие и устаревшие данные. Нет пакета ≠ ПК выключен.
- **Контролируемое переподключение:** при сетевых ошибках ограниченная задержка до следующей автоотправки; при ошибке сертификата, авторизации или протокола автоотправка останавливается.
- **Смена SHA-256 только вручную:** пользователь сверяет отпечаток получателя по независимому доверенному каналу, подтверждает изменение. Старый секрет отправителя очищается; требуется новый ручной ввод. Смена TLS-сертификата не подтверждается приложением автоматически.
- **Секреты не сохраняются в SQLite** и никакие входящие порты не открываются при обычном старте.

## Distributed Probes 2.1 · 0.28.0-dev

- Список до 32 сохранённых **доверенных получателей** по IP, порту и точному SHA-256 сертификата. Только назначения: секретные коды TLS и закрытые ключи не сохраняются. Для возобновления работы получателя после перезапуска требуется новое спаривание с новым сертификатом и кодом.
- Вкладка «Точки наблюдения» → «Доверенные получатели» сохраняет/загружает адреса, но никогда не восстанавливает код доступа автоматически; автоотправка остаётся выключенной при запуске.
- «Журнал измерений» содержит временную шкалу локальных JSON-импортов, экспортов, успешных отправок и приёма по TLS (время UTC, заявленное имя, число измерений). Хранение: до 14 дней и до 2048 событий.
- Состояние входящих наблюдений: свежие (последние 180 секунд), устаревшие, либо отсутствуют за 24 часа; **это не проверка доступности датчика**. Неполученные пакеты не доказывают, что удалённый компьютер не работает.
- Важное ограничение: общий код допуска к TLS-приёмнику **не удостоверяет конкретный компьютер-отправитель**, а имя датчика задаёт сам отправитель. Для аутентификации источника потребуется отдельное спаривание по клиентским сертификатам или идентификаторам.

## Distributed Probes 2.2 — индивидуальные отправители (0.29.0-dev)

- Приём только по явному действию: GUI включает TLS с PIN SHA-256 получателя и **индивидуальными** случайными 256-битными кодами отправителей.
- Каждый ID отправителя имеет свой код. Код показывается только при выдаче; SQLite хранит SHA-256 кодов, не сами коды.
- «Разрешённые отправители» на вкладке «Точки наблюдения»: выдача, перевыпуск и немедленный отзыв доступа без перезапуска приёмника.
- Отозванный ключ не принимается, в том числе если он был отозван, пока запрос передавался.
- Отправитель должен заново вводить личный код после запуска; сертификат приёмника меняется при повторном включении и требует повторной проверки SHA-256.
- Индивидуальный ключ подтверждает только владение кодом, **не аппаратную личность компьютера**. Данные ICMP остаются утверждениями источника.
- Старый bearer API оставлен для программной совместимости, но графический интерфейс использует исключительно strict mode.


Отдельное Windows-приложение для диагностики локальной сети и Wi-Fi. Не связано с модулем Android-приложения BLOODSKY.

## Wi-Fi RADAR 2.4 — обследования за разные даты

- Сравниваются **две разные именованные серии** на том же этаже и только для одинаковых комнаты и SSID (минимум три замера в каждой серии).
- Программа показывает **фактические даты UTC** первых и последних замеров, количества и разницу среднего сигнала Windows в процентных пунктах, без домыслов о скорости.
- На плане можно наложить результаты другой серии полыми контурами, отличая их от заполненных точек текущего обследования.
- HTML-отчёт включает два статичных плана с измеренными точками и таблицу изменений; изображение добавляется только при явном экспорте. JSON-отчёт сохраняет сравнение без изображения.
- Старые точки не перезаписываются, сравнение выполняется только по измеренным точкам за последние 30 дней.

- **Предупреждения о возможном IP-конфликте:** обнаружение изменения MAC-адреса, соответствующего одному IP, в последовательных наблюдениях. Это лишь признак возможного конфликта: смена DHCP, VRRP, клонирование MAC и обновление ARP также способны дать такой результат. Подтверждение требует анализа сети и DHCP/коммутатора.

- **Топология 0.3 (предварительно):** таблица FDB (BRIDGE-MIB/Q-BRIDGE-MIB) — MAC, изученный порт коммутатора, интерфейс IF-MIB, VLAN при однозначном сопоставлении FDB ID. Запись FDB *не* подтверждает прямое физическое соединение; подтверждённые линии карты остаются только из LLDP.
- **Автоопрос SNMP по явному согласию:** интервалы 30/60/120/300 секунд, профили доступа только в оперативной памяти, кнопка «Стоп автоопрос», 30-секундный предел запроса, устаревшие данные скрываются из карты и экспорта.
- **Ручной опрос SNMP/LLDP**: SNMPv3 с SHA-256/AES-128 либо SNMPv2c read-only по явному IP, LLDP-соседи и имена портов. Отображение не сопоставленных соседей отдельно (без выдуманных связей). Пароли и community существуют только в памяти во время опроса, не сохраняются.
- CSV и JSON отчёты. Локальная база `%LOCALAPPDATA%\BLOODSKY-NET\network.db`. Облачной передачи данных нет.

## Новое в 0.5 (экспериментально)

- **SNMP IF-MIB:** вкладка «Порты» показывает 64-битные ifHCInOctets / ifHCOutOctets, ifName, ifOperStatus и ifHighSpeed. Скорость в Мбит/с появляется **после двух успешных опросов** одного коммутатора, при сбросе счётчиков показывается «—». Данные читаются только на явно указанном частном IPv4; нет скрытого перебора сети.
- **Уведомления Windows:** отдельный переключатель на вкладке «События», по умолчанию выключен. Используется локальная библиотека `winotify`; уведомления могут не показываться, если Windows запретила их для приложения/сеанса. Приложение продолжает мониторить сеть без уведомлений.
- **Безопасность:** SNMP-пароли/сообщества остаются только в оперативной памяти и не входят в отчёты; табличные FDB и счётчики не доказывают наличие прямого соединения. Дополнительных требований к правам администратора для SNMP чтения нет.
- **Ограничения:** IF-MIB 64-bit поддерживают не все устройства; без этих таблиц скорость не показывается. Для реальных результатов нужно включить read-only SNMP и проверить совместимость коммутатора. Windows CI проверяет сборку и тесты, но не заменяет испытания на реальных коммутаторах и Windows 10/11.

## Запуск на Windows 10/11

1. Установите Python 3.11 или новее с официального сайта python.org (с опцией Python Launcher `py`).
2. Распакуйте архив и дважды нажмите **`launch_windows.bat`**. При первом запуске скрипт устанавливает зависимости, включая `pysnmp` и `pycryptodomex`, в локальную виртуальную среду.
3. Проверьте автоматически предложенную подсеть, нажмите **«Сканировать»**.
4. После сканирования включённый по умолчанию мониторинг обновляет состояния устройств и Wi-Fi.

### Отдельный EXE без Python на целевом ПК

Запустите **`build_exe_windows.bat`** на Windows с установленным Python. Скрипт соберёт `dist\BLOODSKY-NET.exe` с PyInstaller. Собрать настоящий Windows `.exe` напрямую на Linux нельзя: PyInstaller не кросс-компилятор.

## SNMP/LLDP: получение подтверждённых соседей

1. На управляемом коммутаторе или маршрутизаторе включите LLDP и **SNMP только для чтения**. Введите существующий SNMPv3 пользователь (SHA-256 + AES-128) или read-only community SNMPv2c.
2. Вкладка «Карта сети» → «Опрос SNMP/LLDP». Укажите **конкретный частный IPv4** устройства, версию и реквизиты. Опрос запускается только по нажатию кнопки; сеть целиком по SNMP автоматически не перебирается.
3. Соседи появятся в нижней таблице. Если локальный скан уже знает соответствующий уникальный MAC/hostname, на карте появится синяя сплошная линия с портами. Несопоставленные соседи остаются без IP и без линии.
4. Для остальных управляемых коммутаторов повторите опрос. По умолчанию это **разовые снимки**; для автоматического повторения отметьте «Автоопрос», задайте интервал и подтвердите. Устаревший снимок не отображается как актуальная физическая связь. Остановить автоопрос можно на вкладке «Карта сети».
5. Таблица FDB показывает **изученные MAC и порты**, а не реальные кабельные соединения. Некоторые модели коммутаторов не предоставляют BRIDGE-MIB или Q-BRIDGE-MIB; в таком случае таблица может быть пустой. VLAN неизвестен, если FDB ID не сопоставляется однозначно с VLAN.

Запомненные для автоопроса реквизиты живут только в памяти процесса; приложение их не сохраняет, не экспортирует и очищает при завершении или нажатии кнопки остановки.

Сведения LLDP отражают то, что сообщает устройство; это не измерение состояния кабеля. Порядок портов и имён зависит от поддержки стандартной LLDP-MIB оборудованием. Важно: пароль SNMPv3 не сохраняется и не передаётся в отчёт.

## Ограничения и точность

- Пунктирные связи на карте — **логические**, не реальные кабели. Сплошная синяя линия отображается только при наличии LLDP-записи и однозначного сопоставления удалённого MAC/hostname. Устройства без LLDP, управляемости или SNMP-доступа будут показаны как прежде. Физические связи через неуправляемые коммутаторы могут остаться невидимыми.
- TCP/ICMP/ARP могут не обнаружить устройства за межсетевыми экранами, в других VLAN или в состоянии сна. Отсутствие Ping не всегда означает выключенное устройство.
- Определение типа оборудования производится по DNS-имени и ограниченному набору портов. Производитель выводится лишь для нескольких встроенных известных OUI; остальное честно помечается «Не определён».
- При смене MAC автоматически появляется **подозрение на IP-конфликт**, но не утверждение об установленном конфликте.
- Уровень Wi-Fi в процентах — не абсолютный RSSI в dBm. Номера каналов могут совпадать в 5 и 6 ГГц, поэтому диапазон ориентировочный.
- В Windows 11 получение BSSID и Wi-Fi сетей может требовать включённой геолокации и разрешений доступа к местоположению. Также нужна запущенная служба WLAN AutoConfig.
- Для диагностики работают штатные команды Windows `ping`, `tracert`, `arp`, `route`, `netsh wlan`; драйвер захвата пакетов не нужен.
- При использовании по запросу Windows Defender Firewall может потребовать исключений для проверки TCP. Выполняйте сканирование только своей или разрешённой сети.

## 0.5.0-dev — история и тревоги

- ARP-анализ разделяет одиночную смену MAC (информационная запись) и два и более перехода за 3 минуты (подозрение, а не доказательство IP-конфликта). Предупреждения на обзоре автоматически устаревают через 15 минут. Для подтверждения нужен доступ к DHCP/пакетам/сетевому оборудованию.
- Wi-Fi: в SQLite сохраняются сигнал, SSID, BSSID, канал и состояние не чаще одного раза в 30 секунд. История сигнала показывается графиком при повторном запуске. База ограничивается неделей/20 160 записями; пароли не собираются.
- Ненавязчивый баннер для предупреждений и сбоев внизу окна; можно отключить на вкладке «События». Журнал событий сохраняется независимо от видимости баннера.
- Windows всплывающие системные уведомления, проверка на реальных сетях, разбор DHCP и анализ радиоспектра остаются отдельными задачами — эта версия их не заявляет.

## Новое в 0.6.0-dev — локальная история портов и диагностика DHCP

- **История SNMP-трафика:** после второго достоверного опроса IF-MIB измеренные входящие и исходящие скорости портов сохраняются в SQLite. На вкладке **«Порты»** выберите строку порта: показаны два графика в Мбит/с (синий — входящий, зелёный — исходящий). Данные не отправляются в облако. Строки со сброшенными или отсутствующими счётчиками **не сохраняются как нулевые**.
- **Ограничение объёма:** не более 256 портов за один снимок, максимум 100 000 строк истории за семь дней с периодической очисткой. Удаление старых значений идёт при каждом десятом успешном сохранении и не заменяет резервное копирование.
- **DHCP Windows:** вкладка **«Диагностика» → «DHCP Windows»** показывает полученные через локальный PowerShell/CIM настройки активных IPv4-адаптеров: использование DHCP, сервер, срок аренды (если доступен). Это **пассивная проверка**: без запросов к DHCP-серверам, без захвата пакетов, без прав администратора и без сохранения настроек. Для Linux выдаётся понятное сообщение о недоступности.
- **Круглосуточный режим:** регулярная проверка доступности и SNMP-автоопрос работают **только пока приложение запущено** и пользователь включил соответствующий мониторинг; служба Windows и фоновый агент пока не реализованы. К закрытому приложению никакие фоновые задачи не привязаны.
- **Выпуск:** Windows CI собирает EXE и выполняет тесты. Не следует маркировать эту версию как проверенную на реальных сетях или как стабильную без отдельной приёмки на Windows 10/11 и коммутаторах.


## Новое в 0.7.0-dev — Windows tray и восстановление мониторинга

- **Системный трей** в Windows: значок с командами «Показать BLOODSKY NET» и «Выйти». Пока программа запущена, мониторинг продолжается после скрытия окна. Вкладка «События» → «Сворачивать в трей при закрытии окна» включается **только пользователем**; по умолчанию крестик завершает программу. Если системный трей недоступен, окно не прячется.
- **Автозапуск с Windows:** на вкладке «События» включается отдельно (по умолчанию **выключен**). Используется только `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, без доступа администратора или правки всей системы. Автозапуск сворачивает окно **только при доступном трее**. Для удаления записи достаточно снять галочку. Перемещение EXE после включения автозапуска требует повторного включения функции по новому пути.
- **Восстановление после сбоя:** при неожиданном завершении потока мониторинга интерфейс продолжает работать, событие попадает в журнал, а монитор запускается заново с задержкой 3–60 секунд. Если мониторинг отключён пользователем, повторного запуска нет. Сохранённый список устройств (и шлюз) опрашиваются после нового запуска приложения, если включён мониторинг.
- **Настройки в SQLite:** безопасные флаги интерфейса (мониторинг, предупреждения, оповещения Windows, поведение при закрытии). Пароли SNMP/строки community и профили опроса **не сохраняются** и после перезапуска должны быть введены заново. При повторном открытии приложения SNMP-автоопрос без учётных данных не начинается.
- **Ограничения:** это пользовательский процесс, а **не служба Windows**: выход через «Выйти», завершение сеанса Windows, выключение ПК и отсутствие питания останавливают измерения. Автозапуск работает только после входа пользователя в Windows. Windows CI проверяет код и формирование EXE, но реальную работу меню трея, автозапуска и длительный опрос нужно проверить на Windows 10/11.


## Новое в 0.8.0-dev — надёжность и Windows-установщик

- **Windows Setup:** `BLOODSKY-NET-Setup-0.8.0-dev.exe` собирается на GitHub Actions с Inno Setup 6. Установка выполняется в профиль пользователя (`%LOCALAPPDATA%\Programs\BLOODSKY NET`), без прав администратора, создаёт ярлык меню «Пуск» и по выбору пользователя — ярлык рабочего стола. - **Устойчивость длительного мониторинга:** параллельные запросы Wi-Fi не накапливаются даже при медленном драйвере WLAN; журнальные события ограничены 14 днями или 25 000 записями, очистка раз в 100 событий. Границы истории портов и Wi-Fi из 0.6 сохраняются.
- **Проверка:** `python -m unittest discover -s tests -v` и `python tools/soak_test.py` проверяют выносливость SQLite, защиту от ложных нулевых скоростей и сетевой опрос без реального оборудования. Windows CI собирает portable EXE и Inno Setup installer.
- **Ограничения:** тесты и GitHub Actions не равнозначны длительному испытанию в реальной сети; автономная служба без пользовательского входа в Windows отсутствует. Установщик ещё нужно проверить на Windows 10/11, антивирусе и реальном оборудовании.

## NETWORK TIME MACHINE — этап 0.12.0-dev (история инвентаря)

## 0.13.0-dev — история LLDP-соединений и портов

## 0.14.0-dev — BLOODSKY DETECTIVE, первый доказательный движок

## Wi-Fi RADAR 2.3 — повторное обследование и инженерный отчёт

- Серии измерений задаются вручную, например «До замены AP — октябрь» и «После замены AP — октябрь». Для непосредственного сравнения этапов «До/После» нужно **одно название серии**, один этаж, одна комната и один SSID: разные серии и SSID не перемешиваются.
- Отдельная статистика для каждого SSID, комнаты и этапа. Отсутствие измерения другого SSID не означает, что сеть недоступна.
- JSON/HTML отчёт по выбранной серии: реальные числа измерений, средний/минимальный/максимальный сигнал Windows в процентах, разница «До/После», зоны для повторной проверки только при ≥3 замерах со средним сигналом ниже 45%. Отчёт без паролей, BSSID и внешних сетевых запросов, но содержит SSID и названия комнат.
- Старые записи сохраняются при миграции SQLite, получают метку «Без серии» и **не подмешиваются** в новую серию. Для просмотра исторических результатов можно указать «Без серии». Экспорт CSV включает серию; CSV содержит BSSID.
- Никаких измерений скорости, dBm, спектра или качества неизмеренных точек. «Проблемная зона» — кандидат на дополнительный замер, а не подтверждённая неисправность сети.


## Distributed Probes 2.0 — защищённый обмен TLS (0.27.0-dev)

Во вкладке «Точки наблюдения» доступен опциональный LAN-обмен пакетами свежих ICMP-измерений. Входящий приём **выключен при каждом запуске**. Пользователь вручную задаёт локальный IP (только RFC1918 или loopback) и порт 1024–65535, включает приём и передаёт второму компьютеру через доверенный канал **полный SHA-256 отпечаток сертификата** и **код доступа текущего сеанса**. Получатель проверяет код, а отправитель — именно отпечаток TLS-сертификата *до отправки* кода и данных. Код и сертификат обновляются при новом сеансе, в настройки не сохраняются.

На отправителе вручную вводятся IP, порт, отпечаток и код; после этого доступны кнопка отправки и **отдельно включаемая** автоотправка свежих ICMP-наблюдений каждые 60 секунд. TLS >= 1.2, шифрование средствами Python/OpenSSL. Локальные приватные ключи сертификата находятся во временном каталоге только до остановки приёмника. При выключении приёма или завершении приложения прослушивание и ключи закрываются. Программа не меняет правила Windows Firewall и не обнаруживает другие компьютеры автоматически. JSON-импорт из прошлого выпуска остаётся **неаутентифицированным**.

**Ограничения:** только ICMP-показания текущего мониторинга (до 256 адресов и 512 КиБ за пакет). Получатель отклоняет просроченные, повторные и невалидные пакеты. Владение кодом доступа аутентифицирует доступ к сеансу, но **не доказывает истинность ICMP-наблюдений и не устанавливает причину сбоя**. Без предварительно переданного достоверного отпечатка защищённый обмен невозможен. Передача IP-адресов разрешается только для доверенных компьютеров. Для соединения между двумя компьютерами может потребоваться ручное правило Windows Firewall. Не публикуйте порт в Интернет.
